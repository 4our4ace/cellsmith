# AGENTS.md

Cellsmith is a Claude Code mod, forked from prismantis 0.14.0, that redraws assistant replies with themeable colors: tables, headings, lists, quotes, code, numbers, paths, links and mermaid diagrams. Its diagrams are laid out by Pele and drawn on the terminal's cell grid by pelext (github.com/4our4ace/pelext), our own engine, vendored as `hooks/vendor/pelext.js`. It ships from the cellsmith repository (github.com/4our4ace/cellsmith), whose root is its marketplace; this folder is the plugin.

## Layout

| Path | What |

| `hooks/html.ts` | tables to escaped HTML and tab-separated text, pure |
| `hooks/clipboard.ts` | the macOS and CopyQ clipboard helper sources and their commands, pure |

## Rules

- Bundled code and copied palettes must be MIT. Check the license at the source repo, not a port or fork: GitHub's `license.spdx_id` misses licenses declared only in a README (Gruvbox), and ports can relicense (Tokyo Night's Neovim port is Apache-2.0, the original VS Code theme is MIT).
- Add a dependency only when writing it ourselves is unreasonable. Use its latest release, prefer well-starred maintained projects, and record it in docs/THIRD_PARTY_NOTICES.md. The bundled runtime dependencies today are Pele, pelext, beautiful-mermaid and Prism. esbuild is build-time only. Two external programs can run: the HTML table copy action runs macOS's built-in `osascript`, or an installed and running CopyQ on Linux, and LaTeX math runs RaTeX's `ratex-render`, installed by the person and off until they set `latex`. Nothing else runs.
- Never copy code from other projects, including other mods. Read them to learn the API, then write our own. The one exception is the fork itself: the code inherited from prismantis (MIT, credited in `LICENSE` and the notices).
- No code comments. The why goes in the commit message or PR description.
- Plugin names cannot start with `claude-`, `anthropic-` or `cc-plugin-`, and must not use other products' trademarks (no "Codex" in names).
- No new feature flags or config knobs unless the user asked for them. The exception is looks: a feature with more than one plausible look ships its top 3 or 4 styles behind one option (like `taskStyle`, `promptStyle`), the maintainer picks only the default, every style is a choice in its `/config` picker, and each style has a real screenshot in the README next to the option.
- Feature and fix PRs add their CHANGELOG entry under `## [Unreleased]` and leave the version alone. Only the release commit sets the version, so parallel PRs never fight over it.
- Every user-visible feature ships with a sample in `/cellsmith demo` (`showcaseText` in `hooks/help.ts`), and in the one-screen `/cellsmith` help (`helpText`) when it fits. Extend the help tests in `tests/regressions.test.tsx` so dropping the sample fails.

## Mod API facts that bite

- `$` cannot cross an import. Any function that takes `$` must be declared in `hooks/register.tsx`. `claude plugin validate` does not catch this; `claude plugin test` does ("hooks module did not load").
- A render hook may not write `$.state`. Schedule work with `$.clock.after(0, ...)` and write from there; `read($, atom)` in the render subscribes and redraws when the value lands.
- The built-in `Markdown` element has no theming props, which is why we parse and draw markdown ourselves.
- `TextProps` has color, background, bold, italic, underline, strikethrough, dimColor and inverse. There is no font size on any surface.
- `Image` draws only in terminals with the kitty graphics protocol (kitty, Ghostty); elsewhere it shows its `alt` text.
- Installed (user-tier) plugins cannot change the system prompt: the built-in `sec-default` plugin skips their `prompt.compose`, `prompt.section` and `prompt.context` hooks. Add model-only context through `prompt.submit` instead. Tests do not run `sec-default`, so prove prompt changes in a live `claude --debug` session.
- `userConfig` values are flat primitives. A `string` field with `options` becomes a picker in `/config`.
- Hooks run without Node: no `require`, no bare package imports, no dynamic `import()`. Vendor libraries as one ESM file.
- The authoritative API is the `.d.ts` Claude Code lays in `.claude-plugin/types/` after `claude --plugin-dir .`. Grep it before guessing a prop or event.
- Module size is load time. The runtime reads the whole hooks module when a session loads it: all 35 Pele types (666 KB) made the first render about 0.8 s slower in the test runtime, the 13 bundled types (346 KB) about 0.1 s. Weigh a new diagram type or library against that, and measure the first mount with `claude plugin test` before and after.
- Measure speed in the mod runtime, not in Node. A diagram's code runs a handful of times per session, so it never reaches the optimizing JIT tiers: there, cost tracks the work done, and destructuring, `for...of`, `matchAll` and callback-style array helpers in hot loops cost far more than in warm V8. `node --jitless` on `hooks/vendor/pelext.js` ranks the costs the same way. To time in the runtime, log `performance.now()` deltas from a scratch test file and read them from `claude plugin test` output. A mount in the test kit costs about a second on its own, so time the functions, not mounts.
- The first diagram of a kind pays the engine's first-run cost (a flowchart about 30 ms). `warmDiagrams` in `hooks/register.tsx` pays it in the background after session start. A new common diagram type belongs in `WARMUP` in `hooks/mermaid.tsx`.
- The diagram engine is pelext. Change it in its own repository, under its rules (tests, `npm run compare`, `npm run defects`), and tag a release. Then set the new tag on `pelext` in `../scripts/package.json`, run `npm --prefix ../scripts install` and `build:vendor`, and check `snapshot` and `bench:check`.

## Verify

Run all of these before every commit:

```
claude plugin validate .
claude plugin test .
tsc -p .
```

`tsc` is `../scripts/node_modules/.bin/tsc`. It needs `.claude-plugin/types/`, which appears after running `claude --plugin-dir .` once (or copy `types/claude-code.d.ts` from the plugin-authoring skill to `.claude-plugin/types/claude-code/index.d.ts`). This fork has no CI: run every check by hand. Then see it render for real (`.claude/skills/live-check`): any change to what gets drawn needs a screenshot of `/cellsmith demo` (and `/cellsmith` when the help changed), looked at before the PR opens. Tests prove the tree; only a screenshot proves the look.

Performance and render regressions:

```
npm --prefix ../scripts run snapshot        # demo.md drawn in 3 themes vs tests/snapshots, color and structure
npm --prefix ../scripts run bench:check     # timings vs docs/bench-baseline.json (x1.6, normalized by a calibration loop) and node counts (+10%)
```


After an intended visual change run `snapshot:update` and review the diff; after an intended speed or size change run `npm --prefix ../scripts run bench -- --update`. Claude Code refuses any tree over 20000 nodes and silently draws its own text, so a node-count rise lowers that ceiling (about 500 highlighted code lines, 1000 table rows).

Test-kit gotchas:

- `ui.find({ text: 'x' })` matches substrings, so it returns the parent line. Anchor it: `text: /^x$/`.
- A test whose plugin calls `next(e)` needs an engine stand-in: `on('ui.render', ($, e) => <Text>engine</Text>)`, returning a tree, not `null`.
- Loop visual tests over `['terminal', 'desktop'] as const`.

## Adding an option

1. Add the field to `userConfig` in `plugin.json` with a `title`, a `description` and a `default`.
2. Read it in `resolveStyle` in `hooks/theme.ts`, falling back safely on bad input.
3. Add a row to the README options table.
4. Add a test using `test(name, { options: {...} }, ...)`.
